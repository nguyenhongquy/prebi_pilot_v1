# Provisional Segment Modeling Views

This directory contains candidate-level modeling datasets generated by `data/1.3_dataset_preparation.ipynb`. Use the `*_modeling_*` and `*_scope.csv` files as the canonical training/evaluation views. Do not use the older generic `provisional_{split}_wide.csv` and `provisional_{split}_long.csv` files; they are leftover exports from an earlier run and include rows now excluded from the modeling view.

## Row grain

The source unit is a candidate annotation bundle, identified by `candidate_id`. `segment_id` identifies the underlying text segment. A segment may have multiple candidate rows when alternative annotation bundles exist; do not deduplicate by `segment_id` or combine candidate labels. All candidates for a segment, document, and author are assigned to the same split.

The long view has three rows per candidate, one for each skill dimension. It is a reshaped view of the same candidate data, not three new independent text segments.

## Modeling eligibility

The common modeling view excludes:

- Both candidates for segments with competing `in_scope` and `out_of_scope` labels. These are marked unresolved and are excluded from train, dev, and test classifier views.
- In-scope candidates with unknown skill labels. These are excluded from the common view even though their scope label is available.

Resolved out-of-scope candidates remain in the common view as negative examples for the scope classifier. Their skill targets are not applicable, not skill negatives. In-scope candidates in the common view have known targets for all three dimensions.

Excluded records are retained separately for audit. Do not use audit files as training or evaluation input.

## Labels

`scope_target` is `1` for in-scope and `0` for out-of-scope. `scope_target_known` indicates whether the scope target is usable; it is true for the canonical modeling files.

For in-scope records, each dimension target is encoded as:

| Code | Meaning |
| --- | --- |
| `0` | This dimension is absent from the labeled segment |
| `1` | Band A: original Stufe I or II |
| `2` | Band B: original Stufe III |
| `3` | Band C: original Stufe IV or V |

The band codes are ordered categories, not equally spaced numeric values. Do not interpret them as a regression scale with equal intervals. `known_<dimension>` identifies whether a skill target is known. For out-of-scope rows, skill targets are null/not applicable.

## Which files to use

| Task | File | Recommended rows and target |
| --- | --- | --- |
| Scope classifier (classifier 0) | `provisional_{train,dev,test}_scope.csv` | Use one row per candidate and predict `scope_target`. |
| One of the three skill classifiers, wide form | `provisional_{train,dev,test}_modeling_wide.csv` | Keep `component == in_scope`; use the matching `target_<dimension>` column. |
| One of the three skill classifiers, long form | `provisional_{train,dev,test}_modeling_long.csv` | Keep `component == in_scope` and the desired `dimension`; use `target_value`. Confirm `target_known` is true. |
| Skill presence task | Long form | Use `presence_target`: `0` means dimension absent; `1` means present. |
| Band prediction after presence | Long form | Restrict to `component == in_scope`, desired `dimension`, and `target_value > 0`; predict ordered band classes `1`, `2`, or `3`. |

Do not train the scope classifier on the long file without filtering: its three rows per candidate would triple-count each candidate. Use the scope view for classifier 0. For separate skill models, either select the matching target column from wide form or filter long form to exactly one dimension.

## File inventory

For each split (`train`, `dev`, `test`):

- `provisional_{split}_modeling_wide.csv`: one row per eligible candidate with all target columns.
- `provisional_{split}_modeling_long.csv`: one row per eligible candidate and skill dimension.
- `provisional_{split}_scope.csv`: one row per eligible candidate with the scope target.

Additional outputs:

- `provisional_unresolved_scope_candidates.csv`: both candidate annotations for unresolved-scope segments, with targets masked and assigned split retained.
- `provisional_unknown_skill_candidates.csv`: in-scope candidates excluded because skill labels are unknown.
- `provisional_split_manifest.csv`: document/author split assignments and the `feedback_available` indicator. It includes documents even if all their candidate rows are excluded.
- `provisional_split_summary.csv`: row, segment, document, author, feedback, and exclusion counts by split.
- `provisional_split_label_summary.csv`: scope and skill-target label counts by split.

## Split policy and regeneration

Splits are deterministic with seed `20260929`. Author and document groups are kept intact; group assignment uses resolved, eligible candidate rows for train/dev balancing. The 22 feedback-available reflections are assigned to test, and author/document grouping is applied to their full groups. The test cohort was matched through the restricted de-identified `document_id` and `feedback_available` CSV; this notebook does not read the Moodle feedback workbook.

To regenerate, run `data/1.3_dataset_preparation.ipynb` from the project environment. The notebook expects the private cohort file at `data/private/feedback_cohort/feedback_available.csv` with columns `document_id` and `feedback_available`.

The canonical views were regenerated on 2026-10-06 using normalized author
identities: 62 authors across 239 documents, with 48/8/6 authors in train/dev/test.
Every modeling segment has at least 10 characters after trimming whitespace.
`author_disjoint_provenance.json` records the export hashes and backup location.
The older generic `*_wide.csv` and `*_long.csv` files were not regenerated and
must not be used with the corrected author IDs.

Retraining uses the existing notebook settings through
[scripts/retrain_author_disjoint_classifiers.py](../../scripts/retrain_author_disjoint_classifiers.py):

```sh
.venv/bin/python scripts/retrain_author_disjoint_classifiers.py --model ml
.venv/bin/python scripts/retrain_author_disjoint_classifiers.py --model gbert
```

Model selection uses dev only; test evaluation follows selection. ML models are
saved under protected `PREBI_DATA_ROOT` storage. GBERT uses a fresh checkpoint
directory; completed heads can be reused with `--resume-directory` only when
their split fingerprints match. Existing checkpoints are not overwritten.

These files contain segment text and stable project identifiers. Treat them as controlled research data and follow the repository's data access and release rules. The split manifest also reveals feedback availability; do not publish it without review.
